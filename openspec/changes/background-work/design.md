## Goals / Non-Goals

**Goals:**
- Durable, bounded, observable background work driven by the agent within server-enforced limits.
- Notifications that reach the user in the right place without noise.
- Background confirmations that never block workers and never let the model alter approved actions.

**Non-Goals:**
- Additional executors, Obico, busy detection, notes proposals.

## Decisions

### D1. Scheduler and worker pool
`BackgroundTaskScheduler : BackgroundService` loads the earliest `next_run_at`, waits with `TimeProvider.CreateTimer` (woken early by a signal when tasks change), and enqueues due tasks into a bounded `Channel<TaskId>`; N `TaskWorker`s consume it. Status transitions use optimistic concurrency (`row_version`) so a task never runs twice. On startup, tasks left `running` by a crash become `pending` with a note.
*Alternatives:* Quartz.NET / Hangfire — rejected as too heavy (notes §10).

### D2. Resume model
A run ends in one of: `done` (result set), `waiting` (new trigger: wakeup, event, approval decision, follow-up reply), `failed`. The resume prompt is built from goal + notes + trigger payload only. Approval suspensions append a server-written note (`approval requested: <tool> <args summary> (<pending action id>)`) so the model knows what it is waiting for.

### D3. EventBus and matcher
`EventBus` = one unbounded `Channel<MarshalEvent>` with a single dispatcher that runs `TriggerMatcher` (filters indexed by source + type) and fans matches to the scheduler and to `ConditionalDeliveryTracker`. Sources are hosted services in the integration projects implementing `IEventSource` and publishing through `IEventPublisher` (in Abstractions), so integrations do not reference `Marshal.Tasks`.

### D4. Deliveries and router
`DeliveryDispatcher` validates deliveries at creation (low + voice, followUp on non-voice, `area.*` conditions, critical) and, when a result is ready, evaluates `when` against the HA state cache; pending conditional deliveries are persisted in the task's delivery JSON with state, re-checked on matching `state_changed` events, and expired by a scheduler timer. `NotificationRouter` applies, in order: priority rules → quiet hours / override → DND → presence-based channel choice → coalescing window → per-source and global voice caps → channel delivery → history record with reason.

### D5. Channels
| Channel | Implementation |
|---|---|
| voice announce | HA `assist_satellite.announce` on the chosen satellite |
| voice conversation | HA `assist_satellite.start_conversation` + follow-up record |
| push | HA `notify.mobile_app_*` from the owner's notification targets, with actions for approvals and deep links |
| inbox | `Notification` rows with outcome `inboxed` |

### D6. Approvals
Background guard path: `Guard` receives `ExecutionMode.Background` and, for confirm, calls `IApprovalQueue.EnqueueAsync` (freeze, 10 min TTL, notify) and returns a `Suspend` decision; the runner ends the run as `waiting`. Decisions arrive from the review queue endpoint, the push action handler (nonce check) or a voice follow-up; `ApprovalExecutor` executes the frozen action under the task owner's execution context and schedules the resume with the payload. An expiry timer marks overdue approvals `expired` and resumes the task.

### D7. Backgrounding interactive turns
The conversation runner holds the run in memory; on cap or `agent.move_to_background`, it creates an `AgentTask` (`created_by = user`, origin satellite, deliveries from the turn's context), transfers the in-flight transcript to this single continuation run (the only case where a transcript continues), writes the final SSE event, and hands the run to a worker. Tool list is recomputed with `ExecutionMode.Background`.

### D8. Executor host
`Marshal.ExecutorHost` is a minimal ASP.NET app with its own image: `POST /sessions` (spec, callback URL, callback token), `DELETE /sessions/{id}`, runs `claude -p --output-format stream-json` in a per-session container via the host's (rootless) Docker, in a git worktree; progress and completion are posted to Marshal's `/api/v1/executor/callbacks/{sessionId}` with the callback token. Marshal's `ClaudeCodeExecutor : IExecutor` talks to it with a scoped token stored as a secret.

### D9. Babysitter
`PrintBabysitter` in `Marshal.Integrations.Moonraker` subscribes to printer events through `IEventSubscriber`, snapshots every N seconds (config), calls `IPrintFailureDetector` (`VlmPrintFailureDetector`: `fast` + `vision`, strict JSON verdict), keeps a two-strike counter, pauses via `IPrinterClient`, and sends through `INotificationSender` with source `system:babysitter`.

## Verification (task 1.3, 2026-09-29)

Checked against the HA core source (`dev` branch: `assist_satellite/services.yaml`, `assist_satellite/entity.py`, `assist_pipeline`, `conversation/models.py`) and the companion app docs (notifications basic and actionable). No HA container was run.

- **`assist_satellite.announce`**: target entities of domain `assist_satellite` with the `ANNOUNCE` feature; fields `message` (text, default empty), `media_id`, `preannounce` (default true), `preannounce_media_id`. The call blocks until playback is done. Marshal sends `message` only (TTS by the satellite's pipeline).
- **`assist_satellite.start_conversation`**: target entities with the `START_CONVERSATION` feature; fields `start_message`, `start_media_id`, `extra_system_prompt`, `preannounce`, `preannounce_media_id`. It fails when the satellite's pipeline uses the built-in HA agent (not relevant: Marshal's pipelines use the Marshal agent) and raises `SatelliteBusyError` while the satellite is announcing. The satellite keeps `extra_system_prompt` (or `start_message` when none is given) and consumes it in the **first** pipeline run after the prompt; the pipeline passes it as `ConversationInput.extra_system_prompt`, which custom conversation entities receive. So the `marshal-followup:<nonce>` marker works (as already found in `ha-conversation-integration`); the reply-window fallback stays for satellites or HA versions where it does not arrive. The `start_message` is also added to HA's own chat log as assistant content, which Marshal ignores.
- **`assist_satellite.ask_question`** exists (question, `answers` with sentence matching, returns a response). Not used: its answer matching runs in HA, and Marshal needs the reply as a normal turn.
- **Actionable push**: `notify.mobile_app_<device>` with `data.actions: [{action, title, uri?, behavior?, authenticationRequired?}]`. Android shows at most 3 actions and needs `action: URI` to use `uri`; iOS allows about 10. A pressed action fires the `mobile_app_notification_action` event with `action` (the identifier), `reply_text` (only for `REPLY` / `behavior: textInput`), `action_data` (iOS) and, on Android, the notification's data fields such as `tag`. The event is fired by the companion app through its webhook, so it arrives on HA's event bus and Marshal receives it through its websocket subscription. Marshal encodes the decision and the nonce in the action identifier (`MARSHAL_APPROVE_<nonce>`, `MARSHAL_REJECT_<nonce>`), because `action` is the only field both platforms return, and verifies the nonce server-side; the event itself is not authenticated beyond HA's own access, so the nonce is the proof.
- **Deep links**: tap target is `data.url` (iOS) and `data.clickAction` (Android); both accept relative paths, so Marshal sends both with the result URL. `data.tag` replaces a notification with the same tag; `message: clear_notification` with the tag clears it (used after an approval is decided elsewhere).
- **Priority mapping**: silent push = iOS `push.interruption-level: passive`, Android `importance: low`; `critical` = iOS `push.interruption-level: critical`, Android `channel: alarm_stream` (the companion app's alarm-stream channel) with `priority: high` and `ttl: 0`.

## Implementation notes

- **Run outcomes and re-arming.** A run ends `done`, `waiting` or `failed`. `done` on a `cron` task re-arms it (`waiting`, next occurrence in the owner's time zone); on an `event` task (a watch) it re-arms it without a run time (the matcher makes it due); on `now`, `at` and `after` tasks it is final. `waiting` keeps the task's trigger and sets only `next_run_at` (wakeup) or leaves it empty (approval decision, follow-up reply), so a cron task that waits for an approval keeps its schedule. `failed` is final. An `after(A)` task becomes due when a run of A ends `done`.
- **Claiming.** The worker moves a due task to `running` with the row version it read; a second claim fails with `tasks.conflict` and is dropped. The outcome is applied to a fresh copy (tools may have changed notes during the run); a task cancelled during its run stays cancelled.
- **Cross-owner reads.** The scheduler's due queries (`GetDueAsync`, `GetNextRunAtAsync`, `GetRunningAsync`), the matcher's `GetWatchesAsync` and the delivery tracker's `GetPendingDeliveriesAsync` are the only task queries that bypass the owner filter; they return ids and owners (and a watch's filter) only, and each task is then loaded as its owner.
- **Results.** The final reply of a task run is its result: the first paragraph (up to the first blank line) is `speech`, the whole reply is `body`. The task prompt rules (`TaskPromptContributor`) ask for exactly that shape, so no extra tool is needed.
- **Trigger payloads.** The resumed run sees goal, notes and payload in its user message. Event payloads can carry third-party text (mail subjects, HA attribute values), so they are wrapped as untrusted data and taint the run with kind `event`; payloads written by the server (wakeups, approval decisions) are not.
- **Budgets.** A budget covers one activation of a task: from its trigger through its wakeups until it is done. Recurring tasks (cron, event) start each activation with zero spend, so a daily briefing does not use up a lifetime budget. Unset limits fall back to `tasks.defaultBudget`. A run gets the minimum of what is left of its task's and every ancestor's budget, and at most what is left of the daily cost cap, as `RunLimits` (cost, tokens, model calls, wall time); the agent loop stops with `budget_exceeded` when one is reached (usage counted on the run context, so subagent and advisor calls count). After the run, its spend is added to the task and every ancestor. Over budget before a run: the task fails with `budget_exceeded`. Daily cap reached: the task waits until the owner's next local day (`daily_cap`). The daily cap is per owner (like the advisor's), over all their background runs.
- **Depth, fan-out, intervals.** A child's depth is its parent's + 1 and may not exceed `tasks.maxDepth` (3); a task may have at most `tasks.maxActiveChildren` (5) unfinished children; a cron schedule may not run more often than the minimum wakeup interval (checked over its next occurrences). The minimum wakeup interval is `tasks.minWakeupInterval` (5 min) or the template's `minWakeupInterval`. A child task keeps its parent's origin satellite.
- **Task tools.** Times without an offset are the owner's local time. Inside a task run, `tasks.create` / `tasks.watch` create child tasks (origin satellite and project carry over); `tasks.schedule_wakeup` exists only inside task runs and ends the run `waiting`. Tools accept only their declared arguments, so owner, budget and origin satellite can never be passed. `tasks.cancel` also cancels unfinished descendants. `tasks.run_executor` comes with the executors (task 7.4).
- **Event filters.** A watch's filter is a JSON object: `source` (required), optional `type` and `entity` globs (`*` matches any text), and every other key a payload condition on a dotted path (`to`, `attributes.battery`) whose value is a string glob, a number (also matching numeric strings, because HA states are strings), a boolean, null (field missing) or a list of those (any of them). Strings compare case-insensitively. The filter is validated when the task is created. Example: `{"source": "ha", "entity": "person.alice", "to": "home"}`.
- **Matching.** The bus dispatcher hands each event to the matcher, then to subscribers. The matcher reads the armed watches (`event` tasks that are pending or waiting and not already due) per event, a small indexed query, so there is no cache to keep in step with task changes. A match sets the task `pending`, due now, with the normalized event (`{source, type, entity, time, payload}`) as trigger payload; a watch that is already due or running does not fire again (once per arming). An event with an owner (mail) reaches only that owner's watches; instance-wide events (HA, printers) reach every owner's.
- **HA events.** `state_changed` is published only when the state itself changes (not for attribute-only updates such as a person's GPS position), with `from`, `to` and the new attributes; `mobile_app_notification_action` carries the event data. Both come from the cache's existing websocket connection.
- **Printer events.** Source `printer`, entity = printer name, types `started`, `paused`, `resumed`, `complete`, `error`, `cancelled`, `klippy_shutdown`, `progress` (payload `milestone` 25 / 50 / 75) and `first_layer_done` (only when the slicer reports layers). They are derived from consecutive cache states; the last known state survives a disconnect, so a transition missed while offline is published after the reconnect. The fixture sequences are transcribed from the Moonraker docs (no live printer available).
- **New-mail events.** One IMAP connection per account watches the inbox (read-only, so nothing is marked seen) with IDLE, renewed every 9 minutes, or polls every 2 minutes when the server has no IDLE. Mail already there when the watch starts produces no events; mail that arrived while disconnected does after the reconnect (UIDs above the last seen one, same UIDVALIDITY). Events: source `mail`, type `new_mail`, entity = account alias, owner = account owner, payload `{account, id, from, subject, date}`. The account list is re-read every 5 minutes.
- **Delivery conditions.** `state(<entity_id> <op> <value>)` with `=` / `!=` (case-insensitive text) and `>` / `<` (numeric, checked when the task is saved); `unknown` and `unavailable` states never satisfy a condition. `expires` is `HH:mm` (the next such local time after the result is ready) or a local date and time, and needs a fallback channel (and vice versa).
- **Waiting deliveries.** A delivery whose conditions do not hold when the result is ready is kept in the task's delivery list with `pendingSince` and `expiresAt` (UTC); `agent_tasks.deliveries_pending` indexes such tasks. The tracker re-checks them on every HA `state_changed` for an entity they depend on and every 30 seconds (deadlines, and changes missed while HA was disconnected). A newer result replaces a waiting one. Silent deliveries send nothing.
- **Routing.** Each notification is one `notifications` row with the request (`routing` JSON) and its decision. `critical` (system sources only) goes to voice (requested satellite or presence) and push at once; `low` goes to the inbox, or a silent push when push was requested. `normal` in quiet hours is held (`deliver_after` = end of quiet hours, outcome `held`, then `delivered`) or sent as a silent push, per `notifications.quietHoursMode`; the task's quiet-hours override skips this. Other `normal` notifications wait for the coalescing window (`deliver_after`); later ones with the same requested channel join as `coalesced` and their texts are appended to the first. Notifications with actions or a follow-up never wait. At delivery: voice DND → push; explicit target → that satellite; otherwise presence (home with an occupied room → its satellite, home without → push `no_room`, away → push); then the per-source (`source_voice_cap`) and hourly (`voice_cap`) voice caps; failed voice → push; no push target or failed push → inbox. Reasons are recorded as listed. Fallback deliveries are recorded with outcome `fallback`.
- **Presence.** The owner's `person.*` state decides home / away (`unknown` / `unavailable` = unknown); at home the most recently changed `binary_sensor` with device class occupancy, presence or motion that is `on` and has an area picks that area's `assist_satellite`.
- **Push links.** Push notifications link into the web UI only when `notifications.publicUrl` is set (relative paths would open in HA, not Marshal).
- **Spoken questions.** A `followUp` voice delivery goes through the conversation channel: it stores a follow-up record (owner, 128-bit nonce, satellite, task or pending action, expiry `notifications.followUpTtl`, 2 minutes) and calls `assist_satellite.start_conversation` with the text as `start_message` and `marshal-followup:<nonce>` as `extra_system_prompt`. Linking the reply is part of the conversation path (task 6.4).
- **Scheduler signals.** `ITaskScheduler` (wake, cancel a run) is `TaskSignals`, separate from `BackgroundTaskScheduler`: the scheduler depends on the agent loop, whose tool registry holds the task tools, which signal the scheduler.
- **Approvals.** The guard path is in the agent loop: a confirm-tier call in a task run (not interactive) goes to `IApprovalQueue.EnqueueAsync`, which freezes it with `tasks.approvalTtl` (10 minutes) and the run's task, run id and taint sources, and sends an actionable push (priority `normal`, source `task:<id>`, text = summary plus the reason sentences verbatim, actions `MARSHAL_APPROVE_<nonce>` / `MARSHAL_REJECT_<nonce>`, link `review/<id>`, tag `approval-<id>`). The loop then ends the run, and the task waits without a run time. `ApprovalQueue` also does what D6 calls `ApprovalExecutor`: on approval it executes exactly the frozen tool and arguments (the same helper as the interactive confirmation, re-checking that the tool still exists and is not forbidden) as the task's owner in a background context, and resumes the task (due now, scheduler woken) with the payload `{"approval": {id, tool, summary, decision: approved | rejected, reason?: expired, result? | error?}}`. When the executed tool returns untrusted content, the payload also has `"taint": <kind>` and the resumed run is tainted with it and sees the payload wrapped as untrusted data; other approval payloads are server-written and not wrapped. A decision is one conditional update (`pending` → decided), so the web UI and a push action cannot both decide. A decision while the asking run is still finishing is refused (`approval.task_busy`, try again); a decision for a task that no longer waits drops the approval without executing it. A background loop expires overdue approvals every 30 seconds (as the owner) and resumes their tasks with `rejected` / `expired`; a decision that arrives after the expiry does the same. Push actions are matched by nonce across owners (only approvals of tasks, never interactive confirmations) and decided as the approval's owner; an unknown nonce is logged and ignored. The review queue API is `GET /api/v1/approvals` (frozen tool and arguments, reasons verbatim, taint sources with their first step and the asking run, so the UI links to the tool result that tainted the run) and `POST /api/v1/approvals/{id}/approve|reject`; each decision attempt is audited (`approval.approve` / `approval.reject`, with its outcome). Clearing the push (`clear_notification` by tag) after a decision made elsewhere is not done yet; a stale push action is refused as already decided.
- **Moving a turn to the background.** The agent loop keeps the turn's messages after the system prompt as of the last completed tool round (never a tool call without its result). When the latency cap fires in an interactive top-level turn, or after a round in which `agent.move_to_background(statusMessage)` was called, it hands them to `IBackgroundHandoff` (Core interface, `TaskHandoff` in Marshal.Tasks) and ends the turn with "working on it" (or the status message); the run is recorded `backgrounded` with reason `latency_cap` / `move_to_background`. The tool only flags the request on the run (`RunControl`); the loop acts on it after the round. `TaskHandoff` creates a task for the same user, due now: goal = the user's request, origin satellite = the turn's satellite (so its `denyTools` / `denyConfirm` keep applying), template and project of the turn, and one delivery: voice to that satellite for voice turns (push when the turn had no satellite), inbox for text turns (shown in the web UI). The transcript and the run's taint sources wait in memory (`TaskContinuations`) for the task's first run, which continues them instead of goal + notes (tainted like the original run); later runs follow the normal rule. After a restart the transcript is gone and the task runs from its goal. The handoff is refused while the kill switch is active; then the turn ends as before (latency cap) or says it cannot continue in the background (`background_refused`). The tool is visible only in interactive top-level turns and only when the task system is registered.
- **Follow-up replies.** `ConversationService` asks `IFollowUpReplies` (Core interface, `FollowUpReplies` in Marshal.Tasks) before the session's own pending action. A voice turn is linked by its `followupRef` when the record is known, unexpired, unconsumed and was asked on the turn's satellite; without a reference, the first voice turn from the asking satellite within `notifications.followUpReplyWindow` (20 s, `follow_ups.created_at`) is linked instead: when the marker works, the reply is the first pipeline run after the question and carries it, so the window only applies where it does not arrive. Consuming is one conditional update and stores the turn's session as `linked_session_id` (for HA, a `start_conversation` reply arrives in a new conversation and so a new session). Targets: a pending approval is decided with the confirmation keywords, else the judge, through `IApprovalQueue` (so the frozen action runs and the task resumes); a neutral reply leaves it pending and the turn runs normally. A task waiting for the reply (waiting, no run time, not a schedule or watch) gets `{"reply": {text, satellite}}` as trigger payload and resumes; the user's own words are not untrusted. Both are answered with a fixed reply and no model call. Otherwise a task with a result seeds the turn: a system message with the result body (wrapped as untrusted, since results can summarize third-party content, and the turn is tainted `task_result`) and the speech as an earlier assistant message; the seed is part of that turn only, later turns of the session see the recorded turns. Silence changes nothing: the record expires unconsumed.
- **Executor host.** `Marshal.ExecutorHost` (own image, `src/Marshal.ExecutorHost/Dockerfile`) accepts `POST /sessions` `{repository, prompt, baseBranch?, callbackUrl, callbackToken}` and `DELETE /sessions/{id}`, both behind its own bearer token (a file, compared in constant time). The repository must be a directory name below `executorHost.repositoriesRoot` with a `.git` directory, and the callback URL must lie below `executorHost.marshalUrl`, so a stolen host token cannot make the host post diffs elsewhere. Each session gets a worktree under `executorHost.worktreesRoot` on branch `marshal/<id>` from the base branch (default: the repository's current branch) and one sandbox container: `docker run --rm` on the `executorHost.network` network (an internal network whose only egress is the operator's allowlist proxy), with only the worktree and the repository's `.git` directory mounted (at their host paths, so `/repos` and `/worktrees` are bind mounts with identical paths on the Docker host), and the model key from an env file the host passes through without reading. It runs `claude --bare -p <prompt> --output-format stream-json --verbose --permission-mode bypassPermissions --max-turns <n> --max-budget-usd <x>`. Callbacks: `progress` for each assistant text block (500 characters at most), then `completed` (branch, diff against the base commit capped at 1 MB, Claude's final `result` text, `total_cost_usd`), `failed` (non-zero exit or `is_error`) or `cancelled`. Changes are committed by the host after the run; the worktree is removed at the end and the branch kept only when completed. Shutdown cancels running sessions and waits for their cleanup. The sandbox image (`src/Marshal.ExecutorHost/sandbox/Dockerfile`) is Node with git and `@anthropic-ai/claude-code`. Claude Code CLI facts, checked against the CLI reference and headless docs (2026-09-30): `-p` runs non-interactively; `--output-format stream-json` needs `--verbose` and prints one JSON object per line (`system`/`init`, `assistant` with `message.content[]`, `user` tool results, and a final `result` with `subtype`, `is_error`, `result`, `total_cost_usd`, `session_id`); `--bare` skips local settings, hooks, plugins and OAuth and authenticates with `ANTHROPIC_API_KEY`; `--max-turns` and `--max-budget-usd` bound the run; `bypassPermissions` is safe here only because the container is the boundary. SIGTERM (container removal on cancel) ends the process with exit code 143.
- **Executors in Marshal.** `IExecutor` (Abstractions) has a name, a description for the model, `ValidateSpec`, `StartAsync` (returns the executor's handle and the session's target, e.g. the repository) and `CancelAsync`. `ClaudeCodeExecutor` (`claude_code`, registered only when `executors.claudeCode.url` is set) posts to the executor host with the host token from the secret named in `executors.claudeCode.tokenSecret`; its spec is `{repository, prompt, baseBranch?}` and the repository must be one of `executors.claudeCode.repositories`. `tasks.run_executor(executor, spec, onDoneGoal, deliver?)` is confirm tier, persists, and is hidden without an executor, while the kill switch is active and when the calling task cannot have another child; the executor validates the spec before the confirmation. `ExecutorService.StartAsync` creates the "on done" task first (goal = `onDoneGoal`, a child inside a task run, created `waiting` without a run time, delivered like a moved turn unless `deliver` is given), then the `executor_sessions` row and an `executor_callback` token (no scopes, `task_id` = the on-done task, named after the session), and calls the executor with the callback URL `executors.callbackBaseUrl` + `api/v1/executor/callbacks/<session>`. A failed start revokes the token and fails the session and the task (`executor_start_failed`). Callbacks are authenticated by their own scheme that accepts only callback tokens; the normal token scheme refuses callback tokens, so they work nowhere else. The endpoint checks that the token is the session's own (`executor.wrong_session`, 403); after the session ended the token is revoked, so a reused token gets 401. `progress` changes nothing yet; `completed` creates a `code` proposal when there is a branch and a diff (target = repository, title = the first line of Claude's answer), and every final callback sets the session's status, revokes the token, publishes `executor.completed` / `failed` / `cancelled` (entity = session id, payload with ids, status, target, branch and proposal, not the executor's text) and resumes the on-done task with `{"executor": {session, executor, status, target, branch?, proposal?, review?, summary?, message?}}`. That payload is the report of a model that worked on external content, so the resumed run is tainted `executor` and sees it wrapped as untrusted data. `review` tells the model that the change waits for review in the web UI and can only be merged there; there is no merge tool, so a voice delivery can only announce the review. The executor's reported cost is not counted against the task's budget (it is bounded by the host's `--max-budget-usd`); cancelling the on-done task does not stop the session yet (the web UI's executor view will).
- **Print babysitter.** Enabled per printer (`printers[].babysitter: {enabled, interval}`, interval at least 10 s, default 1 min). `PrintBabysitter` subscribes to the bus: `started` / `resumed` start a watch, `paused`, `complete`, `cancelled`, `error` and `klippy_shutdown` end it; a print already running at startup is watched too. Each interval it captures a snapshot and asks `VlmPrintFailureDetector` (`fast` vision model, else `standard`; JSON response format, temperature 0) for `{"failure": bool, "reason": string}`. Anything else, or no snapshot, is an `unknown` check that breaks the row: only two `failure` verdicts in a row pause. The pause goes straight to `IPrinterClient` (no agent loop, no guard) and ends the watch; the notification is `critical` from `system:babysitter` to the instance owner (printers belong to the instance) in the owner's language, with the reason, whether the pause worked, a link to the printer page, tag `babysitter-<printer>` and the snapshot as image. The phone loads push images without Marshal's cookie, so the image is a shared snapshot link (`/printers/{printer}/snapshots/{id}/shared?signature=`, a Data Protection signature over printer and id that expires after a day; anything else is 404), made absolute with `notifications.publicUrl` like push links and sent as the companion app's `data.image`. The last five checks (time, outcome, reason, snapshot) and the last pause time are kept in memory and shown by `printer.status` and in the printer list (`babysitter`, null when not enabled), which the printer page shows and refreshes every minute while a watch is active. The detector's model calls are not recorded as runs and not counted against a budget.
- **System tasks.** `ISystemJob` (Abstractions) is code-only work named by a task's `job`; `SystemTaskRunner` runs `system` tasks (no agent, no budget) and ends them `done` even when the job fails or throws, with the failure as the result, because `failed` is final and would stop a nightly schedule (an unknown job fails the task). `SystemTaskSeeder` seeds `system-backup`, `system-consolidation` and `system-retention` for the instance owner at startup (after the database is migrated), each only when its job is registered: missing ones are created, existing ones get the configured schedule (`maintenance.*Schedule`) and are armed again unless running, so a cancelled system task comes back on the next start. `BackupJob` writes `/data/backups/<yyyyMMdd-HHmmss>` (UTC) with `VACUUM INTO` (an online, consistent copy while writers continue), a copy of `/data/keys` and `memory-<owner>.ndjson` for every owner (`MemoryExportJob`, the existing NDJSON exporter run as each owner), then keeps the newest `maintenance.backupCopies` dated folders and never touches other folders. `ConsolidationJob` (Marshal.Memory) summarizes, as their owners, the sessions closed in the last day that have no successful `memory_summarizer` run yet, with the same summarizer as session close (user turns and replies only). It is a catch-up for sessions the close path missed rather than a second pass, so the model is not called twice for the same session; it does nothing when the summarizer is disabled. `RetentionPurgeJob` deletes step payloads of runs older than `maintenance.payloadRetention` (30 days; step metadata stays) and runs with their steps older than `maintenance.metadataRetention` (365 days); audit events and project feedback keep their rows without the run link, and memory is never touched.
- **Briefing.** Files only, in `deploy/config.example`: `templates/briefing.md` (standard tier, read-only tools plus `rss.mark_read`, skills `briefing-format` and `rss-digest`), `skills/briefing-format/SKILL.md` (what to gather, the spoken first paragraph of 60 to 90 seconds with the most important first, the written markdown version with mail, draft previews, feed summaries with links; and the on-request path through `tasks_status` / `tasks_run_now`) and `tasks/briefing.yaml`. Tasks live in the database, not in `/config`, so the example task is the arguments of `tasks.create` (cron `0 6 * * *`, voice with `followUp` when `$person` is home and the kitchen is occupied, expiring at 11:00 into a push, and the inbox); the end-to-end test creates the task from that file. The runner already splits a result into its first paragraph (speech) and the whole text (body), and the language is the owner's preference, so nothing briefing-specific is needed; an architecture test keeps it that way.
- **SQLite concurrency.** Workers, web requests and background services write concurrently. Every connection sets `busy_timeout = 5000` (EF Core already creates the database in WAL mode), and the pre-migration copy runs a `wal_checkpoint(TRUNCATE)` first so the copy holds every committed row.

## Risks / Trade-offs

- [Runaway agent loops in the background] → budgets, depth, fan-out, minimum wakeup interval, global daily cap, kill switch; all server-side.
- [Noise from proactive voice] → caps, coalescing, quiet hours, DND, presence; history explains every decision.
- [Approval fatigue] → reasons shown verbatim; taint escalation limited to `persists` tools.
- [HA `extra_system_prompt` not reaching custom agents] → reply-window fallback.
- [Continuation transcript on auto-background is an exception to "no transcript on resume"] → only for the single continuation run of an interrupted turn; later wakeups follow the normal rule.
- [Executor sandbox escapes] → separate host, rootless runtime, network allowlist, per-task tokens.

## Migration Plan

EF migration adds `AgentTask`, `ExecutorSession`, `Notification`, `Proposal`, `FollowUp` and task-related columns on `PendingAction`. System tasks are seeded on startup (idempotent by name). The executor host is optional and deployed separately.
